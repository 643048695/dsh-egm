# 闸门规则（gate-rules）

红黄绿怎么判，以及**哪些能动硬闸、哪些绝对不能**。

## 一、什么能硬卡

判起来没有争议的硬卡条件：

| # | 硬卡条件 | 怎么判 |
| --- | --- | --- |
| 1 | 还没定的事没拍板 | `.egm/<slug>.json` 里 `gaps` 还有没填 `decision` 的项 |
| 2 | 怎么算过验不了 | 缺少明确的验证步骤、观察结果或比对方式（有具体操作/步骤/命令或可观察的界面状态即可，不必强塞数值；仅空洞形容词且无任何验证路径时才卡） |
| 3 | 已核实的硬阻塞项未闭环 | 存在**经代码/源码核实成立（`confirmed`）**的严重阻塞项，且未经过修改复验闭环，或未在用户知情前提下显式确认接受（严禁仅凭单方文字标记绕过验证） |

---

## 二、什么不能硬卡（只能标注）

这一节是**故意写死的**。不写死，插件会退化成教导主任。

1. **已被证伪（`disproven`）的意见** → 经查验实际源码证明不成立、原逻辑已有妥善处理或引用的位置/逻辑不存在的声称，**直接移入审计明细（附录），严禁作为阻塞项，绝对不构成红灯**。
2. **纯措辞、文风、排版意见** → 一律降级为「建议」，永远不阻塞。
3. **未核实（`unverified` / `[无代码依据]`）的意见** → 可以进结果卡与审计明细，但**不许单独构成红灯**；同时**未核实绝不自动等同于合格通过**，必须如实披露证据缺口。
4. **「建议补充更多细节」这类空话** → 直接丢弃，不进结果卡。
5. **用户明确说「你看着办 / 按你的建议来」** → 执行推荐的修复方案并留痕，严禁在未出具方案且未闭环红灯时盲目开工；只有在用户充分了解具体风险和后果后给出明确指令，方可放行已知风险，并强制写入留痕清单。
6. **子代理没跑到的部分、未产出的报告或 partial 失败** → 明确标为「未覆盖/执行失败」，保留证据缺口；**报告缺失绝不代表通过，执行失败绝不是成功**，严禁当作通过，严禁将未完成评审等同于无阻塞项，严禁主会话在同上下文里代评补意见。

## 三、红黄绿判定

```
评审报告产出与声称核验（对照实际源码比对）：
├─ 存在未产出报告 / 执行失败 / 关键范围未覆盖
│  └─ 标为「未覆盖/执行失败」，保留证据缺口；严禁当作通过，严禁主会话代评补意见；
│     必须在正文中如实说明缺口并提示补审，绝不直接判定为绿灯开工
└─ 评审有效完成，所有金鱼声称已比对源码核验（标记 confirmed / disproven / unverified）
   ├─ 已证伪项（disproven）──────→ 移入审计明细备查，不计入阻塞项
   ├─ 存在已核实（confirmed）的阻塞项且未修复闭环 ──→ 红：阻碍开工（必须先出具体修复方案供审阅）
   ├─ 仅有未核实（unverified）的建议项或待澄清项 ──→ 黄：可按建议修改，或用户知情后认风险推进
   ├─ 阻塞项已复验闭环或用户显式知情接受 ─────────→ 绿（附「已接受风险」留痕）
   └─ 没有阻塞项 ─────────────────────────────────→ 绿：方案达标，告知评审通过
```

### 交互准则（证据与方案先行，直接点击动作）

1. **必须在正常可见文本中先出证据与具体修复方案**：
   - 必须在普通文本中完整列出：判定灯号、问题条目（含经实际源码核查后的状态 `confirmed` / `disproven` / `unverified`、行号依据与后果评估；证据缺失则如实注明未核实或无代码依据，不凭空补行号）以及可执行的具体修复方案。绿灯无问题时如实汇报通过，严禁为了凑数凭空编造缺陷。
   - 严禁在用户看到结果和修复方案之前提前弹窗；严禁在没有清晰方案前反问用户技术细节。
2. **严禁例行下一步使用问卷，改用 `egm-actions` 专有动作按钮**：
   - 针对后续操作，**严禁调用 `ask_user_question` 弹出 5 项问卷+提交**；
   - 在正文呈现完证据与方案后，输出插件独占的 `egm-actions` 围栏（包含直选按钮：按推荐修改 `egm-task-revise`、继续复核 `egm-task-review`、按当前方案动手 `egm-task-proceed`、先保留方案 `egm-task-hold`；任务已暂缓时用 `egm-task-resume`，做完用 `egm-task-complete`，已结项要再动时用 `egm-task-reopen`）；
   - 卡片上的 `taskId` / `taskRevision` 只能填命令上下文给出的真实值（`taskRevision` 是方案版本，不是记录修订号）；`egm-task-proceed` 只有在当前图纸与最近一次成功评审内容一致时才可用，图纸改过就必须先补审，或由用户明确二次确认覆盖；
   - 用户若已明确授权当前范围内的修改（如用户已说“按推荐方案改”），直接按既有授权推进，无需额外等待点击。
3. **按判定灯号分流决策**：
   - **绿灯（无阻塞项）**：方案已达标，在正文中告知评审通过、可按既定目标推进；严禁在绿灯时无端弹出「修一轮再来」「直接开工（我认风险）」等无关动作。
   - **黄灯（缺代码依据的阻塞或有待澄清项）**：不是拒绝。在正文完整列明风险、未核实缺口与修复建议后，由用户通过 `egm-actions` 决定「按推荐修改」或「按当前方案动手（认风险）」，绝不强制捆绑无关的交接选项。
   - **红灯（存在已核实的未解决硬阻塞）**：代表方案有致命缺陷，不得盲目开工。AI 必须先给出明确修复方案供用户审阅。提供「按推荐修改」或「先保留方案」；若用户在充分知情后果后仍决定强行放行，必须按第 5 节留痕。
4. **安全许可与开工审批严格区分**：
   - 允许评审（开派发窗口、`egm-review-access` 确认无隔离）仅为子代理审查授权，绝不等于方案审批通过，更不等于源码修改授权；
   - 评审过程严禁改动业务源码；开工修改代码必须建立在展示清晰方案并获用户真实批准的基础之上。

## 四、循环与图纸修订

- **不设人为硬性轮数上限**：删除固定修图纸 2 轮额度的硬限制，严禁在次数用尽时强迫用户接受风险或强制停止。按用户反馈持续修订同一图纸方案。
- **严格区分图纸修订轮数与金鱼派发配额**：修图纸轮数不受人为限额限制；底层金鱼派发次数与许可时效（如 10 分钟/6 次许可、2 小时/20 次窗口）属于安全门控真实配额，两者严格解耦分开。
- **重复无进展时的汇报机制**：当同一问题连续修订仍重复出现且无实质进展时，模型不得擅自强迫放行或草率关闭，而应在正文中诚实汇报具体原因、核心矛盾点并推荐替代修改方案（如缩小范围、换实现机制或人工裁定），交由用户决策是否继续修改或调整方向。

## 五、留痕格式（放行时必须写）

```markdown
## 你认了的风险
- 2026-01-01 15:04 用户确认接受风险开工，接受了：
  - [黄灯] [confirmed] docs/plan.md:18 增量判定未定 —— 后果：改名后全量重传
  - [黄灯] [unverified] 临时文件清理无人负责 —— 后果：磁盘缓慢涨满
  - [审计记录] [disproven] src/cache.ts:50 内存泄漏指责 —— 核查：已有 TTL 自动淘汰，不构成阻塞
```
