# EGM 守门人

> **入口（只有用户能开）**：用户在输入框底部 EGM 入口发起，或输入 `/egm <一句话需求>` 打开派发窗口，kickoff 会把本技能送进来；
> 用户也可以直接手打 `/egm-gate`。模型不该自己起这个流程——但边界要说清：
> **这不是硬隔离**。文件就在包内，模型仍可以直接读它，或者干脆绕过本技能自己写图纸。
> 这里真正能锁的只有金鱼派发通道（`egm_dispatch` 与 `egm_dispatch_batch`）：默认拒绝派发。优先在回复中给出 EGM 插件独占的 `egm-review` 专有块（` ```egm-review ` 或 `<egm-review>JSON</egm-review>`）「是，允许评审／否，先不审」专用按钮，严禁使用通用 `dsh-ui`（防 GenUI 竞争）；点允许后真实命令开启 2 小时/20 次窗口与 10 分钟/6 次许可，随后通过折叠内部上下文通知继续任务，不污染输入框草稿。面板和 `/egm-review-access 确认无隔离` 命令保留为备用。具体按钮格式和处理见 `resources/interaction-contract.md`，不要默认要求用户复制命令。

## 0. 这个技能要干的事

在「想清楚」和「动手写」之间插一道闸：

**出图纸 → 冷启动挑刺 → 用户拍板 → 才开工。**

图纸的标准只有一条：**一个完全没有上下文的人，只靠这份图纸就能干活。**
挑刺的人必须真的没有上下文——这不是修辞，是本次运行成立的前提。

---

## 1. 什么时候用 / 什么时候别用

**用**：
- 用户要新增功能、工具、脚本、插件
- 用户要改一处会改变行为的地方（不只是改文案、改格式）
- 用户说「我想做 X」但还没说清怎么做
- 用户显式说「egm」「守门」「先审方案」

**别用**：
- 纯问答、查资料、解释代码
- 改错别字、调缩进、跑一条命令、修一个明确的 bug
- 用户已经在写代码了 —— 这时只用 `egm-review` 挑刺，别拦他

---

## 2. 铁律（违反任何一条，这次运行就算失败）

1. **不奉承**。不写「很棒」「非常清晰」「好主意」。先说不好的。
2. **不猜**。看不清就去读文件；读不到就说「读不到，需要你给路径」。
3. **每条问题必须能落地并经源码核查**：带 `文件:行号`，对照实际源码核查并标明 `confirmed`（已核实）、`disproven`（已证伪）或 `unverified`（未核实/无代码依据）；`disproven` 移入审计明细不计入 blocker；`unverified` 不自动等同于通过或成立；严禁捏造证据或声称模型保证，保持实际覆盖范围与缺失证据透明。
4. **不可测的词出现即违规**：友好、流畅、合理、尽量、稳定、更好、优雅。必须换成数值、命令或可观察的现象。
5. **每个给用户的选项后面必须有一句「白话代价」**。没有代价的选项不许出现在卡上。
6. **二选一必须带 C**：「都不对，我另有想法」（评审安全许可豁免此规则，使用专用「是／否」按钮；普通文字回复不授权，见交互约定）。
7. **每题给默认推荐**，推荐项排第一。
8. **用户说「你看着办」＝放行**，但必须留痕：写进主文件「已接受的已知风险」。不许因为「标准不可测」就驳回他。
9. **保留评审记录**：图纸、状态、评审房间及报告都可在 `.egm/` 下留存，不承诺固定文件数量。
10. **不替子代理补意见**。子代理超时或失败，就记「这条没跑到」；`manifest.allPassed` 仅代表报告全部完成（仍需阅读发现并裁决，不代表设计通过），`manifest.partial` 不是全通过。严禁主模型在同上下文里代评顶替——那是自我催眠。
11. **不设人为硬性修图纸轮数上限**。删除固定 2 轮额度的硬限制，严禁次数用尽时强迫接受风险或停止；按反馈持续修订同一方案，若重复多轮无进展则如实汇报原因与推荐替代方案，不把 2 轮当硬上限。修图纸轮数与金鱼派发配额严格解耦。
12. **评审阶段不写代码、不改源码**。只出图纸和意见。

## 3. 流程总览

```
A 出图纸（大象/主会话） ──→ 卡1 开工卡 ──→ 用户允许金鱼评审 ──→ B 冷启动挑刺（金鱼子代理） ──→ 卡2 澄清弹窗 ──→ 卡3 结果卡/用户裁决 ──→ 落盘
```

新手首次点击 EGM 入口即讲清完整 4 步流：「描述需求 → 大象整理方案 → 用户允许金鱼评审 → 看报告/用户裁决」。
输入框底部 EGM 入口位置保留（`conversation.input.left`），输入框上方左侧另加工作大象，与右侧鲸鱼同高；保留对话框与文字卡片双启动模式及 `egm.launchMode` 本地记忆。仅在真正满足 `live && working && workingOnEgm` 条件时显示工作态大象与工作动画（但注意不得声称实机已验收）。进度与结果直接在当前对话及现有卡片呈现；后台子会话独立 context，不要求用户手动切窗口。中途不挂起等用户（除了必要的卡片与授权）。

## 4. A 段：出图纸

> **路径基准**：`resources/`、`agents/`、`vendor/` 均以**插件包根**（DSH 的 plugin root）为准，**不是 SKILL.md 同目录**。若找不到文件，应按环境提供的绝对路径清单复查，**绝对不能自己瞎编模板继续**。

1. 建目录 `.egm/`（若不存在）。当前命令已提供图纸路径时，必须沿用该路径；仅未提供路径时才用 `.egm/<slug>.md`。保留同一方案的有效决定，不因后续消息重新建图纸。
2. 骨架照 `resources/design-template.md`（以插件包根为准）。**全篇用大白话写**——一个没背景的人照着就能干，别写行话。四段必须有：
   - **做什么**（一句话 + 3~6 条行为）
   - **不做什么**（边界，至少 2 条）
   - **最怕的三件事，出了怎么办**（断网 / 重名 / 磁盘满 / 并发 / 权限……挑最可能的 3 个，写清怎么发现、怎么兜）
   - **怎么算过**（每条写成「跑啥 + 应该看到啥」，能验、能比对）
3. **怎么算过**必须能验。写不出能验的，就在 A 段把问题攒起来，别硬编。
4. 若用户项目里已有 `.egm/constitution.md`，先读它，图纸不许违反里面写的规则。没有就不建（除非用户主动要）。
5. 攒够问题后再出卡1。**不要边写边问**。
6. 图纸写完 ≠ 可以开工。必须走完 B、C 两段。
7. 图纸落盘后，用插件独占进度块登记当前图纸（` ```egm-progress ` 内 `{"type":"artifact","kind":"design","path":"<图纸路径>"}`），或输入 `/egm-artifact design <图纸路径>`；同一份正式图纸只保留一个当前引用。评审发现的核实与处置按 `resources/interaction-contract.md` §10 走 `/egm-findings`；台账里有未处理 blocker 时「开始实现」会被拦下，除非用户显式输入 `confirm` 覆盖。

## 5. 卡1：开工卡与生命周期

用 `ask_user_question` 让用户选深度：快（1 个角色）、标准（2 个角色，并行）或狠（3 个角色，批次并发）。实际耗时取决于模型和网络响应，不承诺固定时间。用户已明确深度时不必重复询问。

规则：
- 默认停「标准」。用户点「快/狠」就是改档，只改档位，不改别的问题。
- 用户不点、直接说「跑吧」＝按默认档跑。
- 用户说「先不跑」＝停在这里，图纸留着。
- **生命周期与模式记忆**：启动模式由本地 `egm.launchMode` 记忆，同一任务不重复弹出启动模式选择器。后续普通用户消息均是对同一个大象任务 / 同一份图纸的持续调整演进，严禁反复调用 `/egm` 重新起步；只有用户显式明确提出「另一个任务 / 新需求」时才创建新任务。
- 卡1 之后一路跑到卡3，**中间不打断**（除了卡2 的澄清）。

## 6. B 段：冷启动挑刺

### 6.1 先做一次仓库快照（只做一次，不重复）

- 从图纸提到的文件里挑 **2~3 个最关键**的，各摘 30 行以内的「接口签名 + 关键逻辑」，总长 **≤2k token**。
- 存进 `.egm/<slug>.json` 的 `snapshot` 字段，**同时**写进图纸的「附录：代码快照」段——金鱼只读图纸这一个文件，喂料永远只有一个入口。
- **禁止子代理自己 grep/glob 全库**：会抢 I/O、撞限流、把墙钟顶破。

### 6.2 派金鱼通道

- **多角色档优先使用新 `egm_dispatch_batch` 工具**；单角色可继续调用 `egm_dispatch`。
- 多角色批次共用同一份不可变图纸快照；工具在完成后自动 spawn 一个独立的 fresh 汇总子会话整理本批原报告，由插件父侧落盘。汇总不占用额外评审配额。
- **门控与配额（严格保留）**：
  - 授权首选回复内专用按钮：按 `resources/interaction-contract.md` 的规范输出插件独占的 `egm-review` 块（` ```egm-review ` 或 `<egm-review>JSON</egm-review>`，严禁使用通用 `dsh-ui`）「是，允许评审／否，先不审」。EGM 独占解析渲染，不竞争 GenUI；点击经真实命令修改当前会话许可，随后以默认折叠内部上下文通知 AI 继续原任务，不产生可见用户消息，不占用输入草稿。普通文字「是」「好」「同意」「否」不会授权或撤销，不要求用户再复制命令；
  - 亦可在 EGM 面板持续可找到的「评审许可」区阅读风险说明、勾选确认框，并点击「允许本轮评审」按钮（通过原生命令一键开启 2 小时/20 次窗口与 10 分钟/6 次许可，面板展示真实剩余次数与到期时间，到期或用尽就地重新确认续期）；
  - 命令通道提供一键命令：推荐一键命令 `/egm-review-access 确认无隔离`（或带 `grant` 前缀）；撤销用 `/egm-review-access revoke`；
  - 旧分步命令保留作为无 UI / 终端 fallback：`/egm-open` 开 2 小时/20 次窗口，`/egm-unsafe 确认无隔离` 开 10 分钟/6 次许可；
  - 评审按每鱼扣一次配额。批次派发前做预检，**若当前配额不足整批任务，整批直接拒绝**，绝不跑半截。
- **不许**绕过受控通道直接用普通 `subagent` 冒充金鱼。
- 派发被拒绝、超时、失败或汇总失败时，明确报告原因并停止；`manifest.allPassed` 仅代表报告全部完成（仍需阅读发现并裁决），`manifest.partial` 状态不是全通过，**严禁主会话在自己上下文里假装金鱼代评补意见**。

### 6.3 三档参数

| 档 | 派法 | 角色 | 汇总方式 |
| --- | --- | --- | --- |
| 快 | 1 次 `egm_dispatch`（或单项 batch） | `role=logic` | 单角色原报告 |
| 标准 | 优先 `egm_dispatch_batch`（concurrency: 2） | `logic` + `feasibility` | 同批共用不可变快照，独立 fresh 汇总代办整理去重 |
| 狠 | 优先 `egm_dispatch_batch`（concurrency: 3） | `logic` + `feasibility` + `cold` | 同批共用不可变快照，独立 fresh 汇总代办整理去重 |

### 6.4 受控材料新机制

- **range 真实切片**：若指定审查区间，工具在房间内生成真实的文档切片裁剪副本供金鱼阅读，并将行号映射回原文件；澄清：原版在已查 review-loop 仅是指令提示，上游并无强裁剪保证；本地切片裁剪虽经物理裁剪，但**裁剪不是权限隔离**，仍须标注 `strictGoldfishReview: false`，硬性禁越读未证实，不允许把“没输出目录”说成从未运行。
- **sources 普通文件受控复制**：必须指定工作区内普通文件并受控复制副本，禁止整目录盲传；按角色最少材料原则配置。

## 7. 卡2：澄清弹窗

只在真的有没定的事时弹。用 `ask_user_question`，**≤5 题**。

每题固定三段式（照这个顺序写）：

> **<问题>**
> A. <选项>（代价：<一句白话>）← 推荐
> B. <选项>（代价：<一句白话>）
> C. 都不对，我另有想法

规则：
- 没有「白话代价」的题不许弹。
- 推荐项排第一，并在标签里写明「推荐」。
- 用户答完，把答案写进图纸「还没定的，等你拍板」段，**再**出卡3。
- 用户答「你看着办」= 在已有授权范围内按已展示的推荐方案修复并记录修改；不等于接受未展示的风险，也不自动放行未解决阻塞。

## 8. 卡3：结果呈现与专有动作卡

### 8.1 结果与推荐修复方案先行（必须在正常可见回复中完整呈现）

金鱼评审完成后，**严禁在用户看清结果前过早弹出抽象的问卷**。模型必须首先在正常可见回复正文中完整清晰地呈现：
1. **评审发现与代码核查清单**：将金鱼声称对照实际源码与当前版本逐一核对，标明核验状态与角色行号出处：
   - `confirmed`（已核实成立）：与实际代码对齐，有因果链支撑，作为阻塞项（blocker）或整改依据；
   - `disproven`（已证伪/不成立）：经查验源码证明原逻辑已有防御或声称不实，放入审计明细（附录）供查验，**绝不计入阻塞项，不影响红绿灯判定**；
   - `unverified`（未核实/无代码依据）：因缺少对应源码或未覆盖而未核实，如实披露证据缺口，**不自动等于确认成立，亦不自动等同于合格通过**；
   - 严禁捏造证据，不得宣称模型绝对保证，实际代码覆盖与缺失证据必须透明呈现。
2. **具体的、可落地的推荐修改方案**：针对每项阻碍具体给出改动方案与依据，而不是仅有抽象的“修一轮”；
3. **结果卡（卡3）**：直观展示红/黄/绿灯与关键验收项：

```dsh-ui
{"title":"结果卡 · <slug>","gap":12,"items":[
  {"type":"callout","tone":"warning","content":"黄灯 · 现在开工有 2 个坑，不会立刻炸，但一周后会疼。"},
  {"type":"list","items":[
    "[阻碍] [confirmed] src/app.ts:42 — 备份失败没重试 — 断网时静默丢数据",
    "[建议] [unverified] 「支持增量备份」没说怎么判增量"
  ]},
  {"type":"steps","steps":[
    {"title":"断网 10 秒后自动重试并留下日志"},
    {"title":"增量判定有明确依据（修改时间 or 哈希）"},
    {"title":"恢复到新目录后能跑通一次完整恢复"}
  ]}
]}
```

- `callout.tone` 只用三档：`success`（绿灯）/ `warning`（黄灯）/ `error`（红灯）。判定规则见 `resources/gate-rules.md`。
- 摘要可优先列最重要的 3 条；全部未解决阻塞必须披露，可在正文或有明确链接的完整报告中列出。没有发现就明确写未发现，不凑数，不编造位置。
- 验收清单按任务实际需要列出，每条有可执行步骤或可观察结果，不机械凑 3~5 条。
- 若修复已在用户明确授权范围内且路线未变，展示结果和修法后直接继续，不重复请求批准；只有新范围、关键分歧或必要权限才询问。

### 8.2 后续操作：插件独占 `egm-actions` 专有围栏直接点击按钮（取代问卷）

- **严禁对例行下一步调用 `ask_user_question` 问卷**（如弹出修改/复核/接受部分/替代路线/放弃等 5 项问卷）。所有例行后续选择转为直接点击的按钮。
- **输出插件独占的 `egm-actions` 围栏**：
```egm-actions
{
  "title": "评审后续操作",
  "taskId": "<命令上下文给出的真实 taskId，不知道就省略>",
  "taskRevision": "<命令上下文给出的方案版本整数，不知道就省略>",
  "items": [
    { "type": "button", "label": "按推荐修改", "action": "egm-task-revise" },
    { "type": "button", "label": "继续复核", "action": "egm-task-review" },
    { "type": "button", "label": "按当前方案动手", "action": "egm-task-proceed" },
    { "type": "button", "label": "先保留方案", "action": "egm-task-hold" }
  ]
}
```
- **规则与执行**：
  - 仅按需展示当前场景真正相关的按钮（如无需复核时不放「继续复核」，无修改方案时不放「按推荐修改」），不机械凑齐；任务已暂缓时用 `egm-task-resume`，收尾用 `egm-task-complete`，已结项要再动时用 `egm-task-reopen`；
  - `taskId` / `taskRevision` 只能填命令上下文给出的真实值（`taskRevision` 是**方案版本**整数，不是记录修订号），严禁照抄示例或写 `rev-1` 这类编号；两项都不知道就都省略，插件点按时读取当前任务；
  - 具体的替代路线（alternative route）在正文自然语言中阐述，由用户在常规消息中提出，不设假按钮；
  - **无 GenUI 依赖，严禁使用 `dsh-ui` 输出任务动作卡**。EGM 自有动作渲染器负责解析渲染；模型完全没输出动作卡时，底栏「当前方案」面板仍按后端给出的可用动作执行；
  - 用户点击按钮直接在当前会话内通过远程 RPC 触发固定的宿主命令 `/egm-action revise|review|proceed|hold|resume|complete|reopen <taskId> <taskRevision>`，随后通过 steer context 推进任务；重复点击或刷新后重试复用同一操作记录，不会变成两次执行；
  - 「按方案开始实现」只在当前图纸与最近一次成功评审内容一致时可用；图纸改过要先补审，或由用户明确二次确认覆盖（后端按内容哈希核对，不靠模型自述）；
  - **「先保留方案」只阻止后续排程**：正在运行的金鱼/工具不会被中止；没有可靠的宿主停止接口，禁止提供「停止」按钮或声称已经停下；
  - 用户若已明确授权当前范围内的修改（如用户已说“按推荐修改”），直接按既有授权推进，无需额外等待点击；
  - 方案版本（`taskRevision`）只在实质改需求时推进；普通对话、复核、暂缓都不改版本也不解除暂缓。版本更新仅使受改动影响部分的评审结论失效，未受影响部分保持有效，不得声称旧报告审过了新内容。

## 10. 不要做

- 不要复刻原版的 5 轮串行循环、7 个子技能、一堆报告文件
- 不要在评审阶段改代码或提 PR
- 不要用「看起来 / 大致 / 基本上 / 应该没问题」
- 不要把子代理的整段原话贴给用户——每条压到 50 字以内
- 不要因为「验收标准不可测」拒绝干活——改成「给推荐 + 让他一句话放行」
- 不要把评审安全许可（是否允许评审）当成需求问题强行包装成复杂三选项 `ask_user_question`；安全授权支持直接答「是」/「否」即时放行或拒绝（详见 `resources/interaction-contract.md`）
- 不要在用户看清具体缺陷与推荐修复方案前过早弹出抽象选择问卷；严禁在卡3决策中机械硬塞无意义的第三选项（如无交接需求的交接说明）；子代理失败或超时如实报告缺口，严禁假装全跑通或全通过
- 不要在评审中途加无关确认；开工选择、必要澄清和真正有路线分歧的后续决定才使用 `ask_user_question` 收到答案，不重复询问已作出的决定；一次运行最多三张展示卡
