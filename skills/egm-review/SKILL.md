# EGM 挑刺（对已有文档）

## 0. 它是什么

只做一件事：**拿一份已经写好的东西，让完全没有上下文的人挑刺，然后告诉你「能不能开工」。**

它不写代码、不改你的文档、不替你补方案。
它和 `egm-gate` 共用同一套角色与规则，区别是 `egm-gate` 从「还没图纸」开始，它从「已有图纸」开始。

> **路径基准**：`resources/`、`agents/`、`vendor/` 均以**插件包根**（DSH 的 plugin root）为准，**不是 SKILL.md 同目录**。若找不到文件，应按环境提供的绝对路径清单复查，**绝对不能自己瞎编模板继续**。当前对话可见真实 working 态工作提示动画，但不得声称实机已验收。

---

## 1. 输入

用户会给你一个路径，或者把内容贴出来。三种情况：

- **给路径** → 直接读。读不到就说「读不到，请给绝对路径」，不许猜。
- **贴内容** → 先存成 `.egm/<slug>.md` 再往下走（子代理要读文件，不能读聊天记录）。
- **没给** → 问一句「审哪个文件？」然后停。

---

## 2. 铁律

和 `egm-gate` 完全一致，最要紧的准则在这里复述：

1. 不奉承，先说不好的。
2. 每条问题带 `文件:行号`，对照实际源码核查并标明 `confirmed`（已核实）、`disproven`（已证伪）或 `unverified`（未核实/无代码依据）；`disproven` 移入审计明细不计入 blocker；`unverified` 不自动等同于通过或成立；严禁捏造证据或声称模型保证，保持实际覆盖范围与缺失证据透明。
3. 不可测的词（友好/流畅/合理/尽量/稳定）出现即违规。
4. 不替子代理补意见。没跑到的就写「没跑到」；`manifest.allPassed` 仅代表报告全部完成（仍需阅读发现并裁决，绝不代表设计通过），`manifest.partial` 或执行失败绝不是通过，严禁主会话代评。
5. 证据与方案先行：必须先在正常可见回复中呈现审查结果、具体依据（文件:行号、代码核查状态）、严重后果与**可执行的修复方案**；用户已授权当前范围内修改时直接推进，只有出现关键路线分歧时才提供动作选项。
6. 不设人为硬性修图纸轮数上限：删除固定 2 轮额度的硬限制，按反馈持续修订同一方案；重复无进展时汇报具体原因与替代建议，不强迫接受风险或停止。修图纸轮数与金鱼派发配额严格解耦。
7. 授权与审批严格区分：安全许可（允许评审）绝不等于代码修改或开工授权；开工必须在展示完整方案并获用户真实批准后进行。
8. 保留 `.egm/` 下的图纸、状态和评审报告，不承诺文件恰好只有两份。
9. 两道门严格执行，批次配额不足整批先拒绝，汇总代办不占评审配额。

## 3. 流程

### 3.1 卡1 选深度与生命周期

用 `ask_user_question` 询问评审深度：快（1 个角色）、标准（2 个角色，并行）或狠（3 个角色，批次并发）。实际耗时取决于模型和网络响应，不承诺固定时间。如果用户已经说明深度，不要重复询问。
启动模式记忆生效，同任务不重复弹出启动模式选择器。后续普通用户消息是对当前同一方案的持续调整微调，严禁反复调用 `/egm` 重新起步；仅在显式指示「新任务」时开新任务。

### 3.2 快照

只摘 2~3 个关键文件的接口与关键逻辑，**≤2k token**，写进 `.egm/<slug>.json` 的 `snapshot`。
禁止子代理自己全库 grep/glob。

### 3.3 派子代理

同 `egm-gate` 第 6.2 节：
- **多角色档优先使用新 `egm_dispatch_batch` 工具**；单角色可继续调用 `egm_dispatch`。
- 多角色批次共用同一份不可变图纸快照；工具在完成后自动 spawn 一个独立的 fresh 汇总子会话整理本批原报告，由插件父侧落盘。汇总不占用额外评审配额。
- **门控与配额（严格保留）**：
  - 授权首选界面操作：引导用户在 EGM 面板持续可找到的「评审许可」区阅读风险说明、勾选确认框，并点击「允许本轮评审」按钮（通过原生命令一键开启 2 小时/20 次窗口与 10 分钟/6 次许可，面板展示真实剩余次数与到期时间，用尽就地重新确认续期）；
  - 亦可使用命令通道：推荐一键命令 `/egm-review-access 确认无隔离`（或带 `grant` 前缀）；撤销用 `/egm-review-access revoke`；
  - 旧分步命令保留作为无 UI / 终端 fallback：`/egm-open` 开 2 小时/20 次窗口，`/egm-unsafe 确认无隔离` 开 10 分钟/6 次许可；
  - 评审按每鱼扣一次配额。批次派发前做预检，**若当前配额不足整批任务，整批直接拒绝**，绝不跑半截。
- **受控材料控制**：
  - range 若指定，工具在房间内生成真实切片裁剪副本并映射行号；澄清：原版在已查 review-loop 仅是指令提示，上游无强裁剪保证；本地裁剪不是权限隔离，仍标 `strictGoldfishReview: false`，硬性禁越读未证实，不允许把“没输出目录”说成从未运行；
  - sources 必须指定工作区内普通文件受控复制副本，禁止整目录盲传，最少材料原则。
- 派发失败、超时或被拒绝时停下并说明；`manifest.allPassed` 仅代表报告全部完成（仍需阅读发现并裁决），`manifest.partial` 状态不是全通过，严禁主会话在自己上下文里冒充金鱼代评。

档位与角色：

| 档 | 派法 | 角色 | 汇总方式 |
| --- | --- | --- | --- |
| 快 | 1 次 `egm_dispatch` | `logic` | 单角色原报告 |
| 标准 | 优先 `egm_dispatch_batch`（concurrency: 2） | `logic` + `feasibility` | 同批共用不可变快照，独立 fresh 汇总代办整理去重 |
| 狠 | 优先 `egm_dispatch_batch`（concurrency: 3） | `logic` + `feasibility` + `cold` | 同批共用不可变快照，独立 fresh 汇总代办整理去重 |

### 3.4 卡2 澄清（可选）

只有当评审发现「不看你的回答就没法判」的问题时才弹，≤5 题，每题带白话代价与推荐选项。
如果问题都能从文件里查到，就别弹——直接查。不机械强制无意义的“C 选项”，只在确有不同主张时提供自定义。

### 3.5 卡3 结果呈现与专有动作卡

```dsh-ui
{"title":"结果卡 · <文件名>","gap":12,"items":[
  {"type":"callout","tone":"success","content":"绿灯 · 没有阻碍项，可以开工。两条建议列在附录里。"},
  {"type":"list","items":[
    "[建议] [confirmed] docs/plan.md:18 — 「失败时优雅降级」不可测 — 建议改成具体退避秒数",
    "[建议] [unverified] 没写谁负责清理临时文件"
  ]},
  {"type":"steps","steps":[
    {"title":"断网 10 秒后自动重试并留日志"},
    {"title":"增量判定写成哈希或修改时间"},
    {"title":"恢复到新目录能跑通一次"}
  ]}
]}
```

状态判定严格看 `resources/gate-rules.md`：
- 红灯：存在经源码核验成立（confirmed）的有代码依据阻碍项，且方案未妥善处置。
- 黄灯：有阻碍项但未核实或缺代码依据，或验收清单有不可测项（用户可明确接受后放行）。
- 绿灯：没有阻碍项。

**交互铁律：证据与方案先行，严禁提前弹窗**：
1. **先在正常文本中展示完整证据与修复方案**：
   - 评审发现与代码核查清单：将金鱼声称对照实际源码与当前版本逐一核对，标明核验状态（`confirmed` / `disproven` / `unverified`）与角色行号出处；`disproven` 移入审计明细备查，绝不计入 blocker 或影响红绿灯；`unverified` 透明披露证据缺口，不自动等于确认成立亦不自动合格通过；严禁编造证据，不得宣称模型绝对保证，实际代码覆盖与缺失证据透明呈现。
   - 必须逐条呈现判定灯号、真实证据、严重后果与 AI 具体的、可落地的修改方案。
2. **角色分工与动作含义**：
   - **金鱼只做独立审查**，绝不执行修复或写代码，不要新增所谓的施工金鱼；大象（主会话）负责整理方案与修改设计图纸；
   - `egm-task-revise`（按推荐修改）：**只改设计文档/图纸，绝不改动任何业务源码**；
   - `egm-task-proceed`（按当前方案动手）：明确为「按方案开始实现」，此时才获准开始编写代码/改动源码，且**绝对不绕过未闭环的阻塞项**；
   - `egm-task-review`（继续复核）：仅用于针对修改后的图纸进行针对性补审；
   - `egm-task-hold`（先保留方案）：保留当前图纸与方案状态。
3. **后续操作：插件独占 `egm-actions` 专有围栏直接点击按钮（取代问卷）**：
   - 严禁调用 `ask_user_question` 弹出例行下一步问卷（如修改/复核/接受部分/替代路线/放弃等 5 项问卷）。所有例行后续选择转为直接点击的按钮：
```egm-actions
{
  "title": "评审后续操作",
  "taskId": "<命令上下文给出的真实 taskId，不知道就省略>",
  "taskRevision": "<命令上下文给出的方案版本整数，不知道就省略>",
  "items": [
    { "type": "button", "label": "按推荐修改", "action": "egm-task-revise" },
    { "type": "button", "label": "继续复核", "action": "egm-task-review" },
    { "type": "button", "label": "按当前方案动手", "action": "egm-task-proceed" },
    { "type": "button", "label": "先保留方案", "action": "egm-task-hold" }
  ]
}
```
   - 仅按需展示当前场景真正相关的按钮，不机械凑齐；具体替代路线在正文自然语言中阐述，由用户在常规消息中提出，不设假按钮；
   - `taskId` / `taskRevision` 只能填命令上下文给出的真实值（`taskRevision` 是**方案版本**整数，不是记录修订号），严禁照抄示例或写 `rev-1`；都不知道就两项都省略；
   - **无 GenUI 依赖，严禁使用 `dsh-ui` 输出任务动作卡**。EGM 自有动作渲染器负责解析渲染；模型没输出动作卡时，底栏「当前方案」面板仍按后端给出的可用动作执行；
   - 用户点击按钮直接在当前会话内通过远程 RPC 触发固定的宿主命令 `/egm-action revise|review|proceed|hold|resume|complete|reopen <taskId> <taskRevision>`，随后通过 steer context 推进任务；重复点击或刷新重试复用同一操作记录；
   - 「按方案开始实现」只在当前图纸与最近一次成功评审内容一致时可用；图纸改过要先补审，或由用户明确二次确认覆盖（后端按内容哈希核对）；
   - 「先保留方案」只阻止后续排程，正在运行的金鱼/工具不会被中止；没有可靠停止接口，禁止提供「停止」按钮或声称已停下；
   - 用户若已明确授权当前范围内的修改（如用户已说“按推荐修改”），直接按既有授权推进，无需额外等待点击；
   - 方案版本（`taskRevision`）只在实质改需求时推进；普通对话、复核、暂缓都不改版本也不解除暂缓。版本更新仅使受改动影响部分的评审结论失效，未受影响部分保持有效，不得声称旧报告审过了新内容。

### 3.6 落盘

同 `egm-gate` 第 9 节：`.egm/<slug>.md`（五段 + 折叠附录）+ `.egm/<slug>.json`（断点状态）。

## 4. 不要做

- 不要改成「帮用户重写这份方案」。他让你挑刺，不是让你代笔。
- 不要因为文档写得短就判绿灯——短不等于清楚。
- 不要在一次运行里审第二份文件（重开一次）。
- 不要在评审阶段动源码。
- 不要在结果卡里放超过 3 条「致命问题」——多了等于没有重点。
- **不准在普通文本未展示证据和修复方案前提前弹窗 `ask_user_question`**。
- **不准对例行下一步调用 `ask_user_question` 问卷，严禁使用问卷+提交替代直接动作按钮**。
- **不准设定人为硬性修图纸轮数上限（如固定 2 轮额度），严禁在次数用尽时强迫用户接受风险或强制停止**。
- **不准误将金鱼当成施工角色，金鱼只做独立审查不写代码；严禁在 `egm-task-revise` 阶段修改源码**。
- **不准在绿灯无阻碍时弹出「修一轮再来」或要求用户认风险**。
- **不准将报告收齐（allPassed）说成设计通过，不准将报告缺失或执行失败当作通过**。
